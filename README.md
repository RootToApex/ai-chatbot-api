# AI 챗봇 API

Kotlin + Spring Boot 기반 챗봇 API 서버. 회원 인증(JWT), OpenAI 연동 대화(스트리밍 포함), 피드백, 관리자 분석·보고 기능을 제공합니다.

## 실행 방법

```bash
docker compose up -d --wait   # PostgreSQL 15.8
./gradlew bootRun             # 애플리케이션 실행
./gradlew test                # 테스트 (OpenAI 키 불필요 — 결정론적 fake 사용)
```

- OpenAI 실 호출에는 `OPENAI_API_KEY` 환경변수가 필요합니다 (`.env.example` 참고). 키가 없으면 대화 생성 API는 명시적 503을 반환합니다 — 그 외 전 기능은 키 없이 동작합니다.

## 요구사항 분석

요구사항은 네 덩어리(인증 / 대화·스레드 / 피드백 / 분석·보고)이고, 선택·후순위 표시가 없습니다. 따라서 **전부 필수로 취급하고 넓게 먼저 깐 뒤 깊이를 더하는 순서**로 잡았습니다. 한 기능을 완성도 높게 다듬느라 다른 요구를 비우는 것이 가장 나쁜 결과라고 판단했습니다.

구현 순서는 의존 관계를 따랐습니다. **인증 → 대화·스레드 → 피드백 → 분석·보고**. 피드백은 대화가 있어야 달 수 있고, 보고서는 대화와 사용자가 있어야 집계됩니다. 커밋을 이 순서대로 쪼갠 것도 의도적입니다 — `git log`가 곧 "무엇을 먼저 했는가"의 기록이 됩니다.

요구사항에서 판단이 필요했던 지점은 세 가지였습니다.

**1. 스레드의 정의.** "OpenAI에 보낼 지난 대화 목록의 단위"이자 "마지막 질문 후 30분"으로 갈리는 경계입니다. 즉 스레드는 사용자가 만드는 것이 아니라 **질문 시각으로부터 파생되는 것**입니다. 그래서 스레드 생성 API를 따로 두지 않고, 대화 생성 시 서버가 경계를 판정합니다.

**2. "대화 목록을 스레드 단위로 그룹화"와 페이지네이션의 관계.** 그룹화가 요구되므로 페이지의 단위는 대화가 아니라 **스레드**여야 합니다. 대화를 페이징하면 한 스레드가 페이지 경계에서 잘려 그룹이 쪼개집니다. 정렬 기준 "생성일시"는 원문 그대로 스레드 생성일시로 해석했습니다(30분 규칙은 스레드를 *나누는* 기준이고, 정렬은 나뉜 스레드를 *배열하는* 기준이라 서로 다른 축입니다).

**3. 확장 가능해야 한다는 요구.** 이 문장을 "지금 모든 것을 일반화하라"로 읽지 않았습니다. 실제로 바뀔 축만 골라 경계를 뒀습니다 — provider 교체(`AiProvider`), 보고서 출력 형식(`ReportGenerator`), 그리고 향후 사내 문서 학습(RAG)이 들어올 자리입니다. 나머지는 요구된 형태로 단순하게 구현했습니다.

### 확장 지점

| 바뀔 축 | 지금 구조 | 바뀔 때 손대는 곳 |
|---|---|---|
| AI provider 교체 | `ai/domain/AiProvider` 포트 + `ai/infrastructure/OpenAiProvider` 어댑터 | 어댑터 하나 추가. 도메인·유스케이스 무변경 |
| 사내 문서 학습(RAG) | `AiChatRequest.context`가 참고 문서 자리 | 문서·임베딩·검색을 별도 컨텍스트로 추가하고 검색 결과를 context에 주입 |
| 보고서 형식(CSV 외) | `report/domain/ReportGenerator` 포트 | 구현체 추가 |
| 모듈 분리 | 도메인별 `domain / application / api` 패키지, 의존 방향 단방향 | 패키지 경계가 곧 모듈 경계라 파일 이동 없이 Gradle 모듈로 승격 가능 |

**멀티모듈로 가지 않은 이유**: 초기 구현 단계에서 모듈 분리는 파일 이동·의존 방향·컴포넌트 스캔 재설정에 시간을 쓰고, 실패하면 빌드가 죽습니다. 요구된 기능을 모두 동작시키는 것이 먼저이므로, 같은 의존 규칙을 패키지로 강제하고 승격 경로를 남기는 쪽을 택했습니다.

## 설계 계획

### 요구사항 매트릭스

| ID | 기능 | 우선순위 | 완료 판정 |
|---|---|---|---|
| A1 | 회원가입 | 필수 | 이메일 중복 409, 성공 201 + 사용자 정보(비밀번호 제외) |
| A2 | 로그인 | 필수 | 일치 시 200 + JWT, 불일치 401 |
| A3 | JWT 인증 | 필수 | 가입/로그인 제외 전 요청에 유효 토큰 없으면 401 |
| C1 | 스레드 자동 생성/재사용 | 필수 | 첫 질문 또는 마지막 질문 후 30분 경과 시 신규, 이내면 기존 유지 |
| C2 | 대화 생성 | 필수 | 질문→답변 응답, isStreaming/model 옵션 동작 |
| C3 | 대화 목록 조회 | 필수 | 스레드 단위 그룹화, 본인만(admin 전체), 정렬+페이지네이션 |
| C4 | 스레드 삭제 | 필수 | 본인 스레드만 204, 타인 접근 403/404 |
| F1 | 피드백 생성 | 필수 | 본인 대화만(admin 전체), 동일 (user,chat) 중복 409 |
| F2 | 피드백 목록 조회 | 필수 | 본인만(admin 전체), 정렬+페이지네이션+긍정/부정 필터 |
| F3 | 피드백 상태 변경 | 필수 | admin만, pending/resolved |
| R1 | 활동 기록 | 필수 | 요청 시점 기준 최근 24h 가입/로그인/대화 수 (admin) |
| R2 | 보고서 CSV | 필수 | 최근 24h 전체 대화+작성자 CSV (admin) |

구현 순서: A → C → F → R (git log가 곧 우선순위 기록)

### API

모든 경로 `/api/v1` 접두. 시각은 UTC(timestamptz) 기준.

| 메서드 | 경로 | 권한 | 요청 | 응답·상태코드 |
|---|---|---|---|---|
| POST | /auth/signup | 공개 | email, password, name | 201 사용자 정보 / 400 / 409 |
| POST | /auth/login | 공개 | email, password | 200 accessToken / 401 |
| POST | /chats | 인증 | question, isStreaming?, model? | 201 chat / isStreaming=true면 200 text/event-stream / 400 / 503(LLM 불가) |
| GET | /chats | 인증 | page, size, sort=asc\|desc | 200 스레드 그룹 페이지 (admin은 전체 유저) / 400 |
| DELETE | /threads/{id} | 인증 | - | 204 / 403 / 404 |
| POST | /feedbacks | 인증 | chatId, isPositive | 201 / 403 / 404 / 409 |
| GET | /feedbacks | 인증 | page, size, sort, isPositive? | 200 페이지 / 400 |
| PATCH | /feedbacks/{id}/status | admin | status=pending\|resolved | 200 / 400 / 403 / 404 |
| GET | /admin/activity | admin | - | 200 {signupCount, loginCount, chatCount} |
| GET | /admin/report | admin | - | 200 CSV 다운로드 |

인증: `Authorization: Bearer <JWT>`. 401(미인증)/403(권한 부족)은 전 엔드포인트 공통.

### 데이터 모델

- **users** — id PK, email unique, password(해시), name, role(member|admin), created_at
- **threads** — id PK, user_id FK, created_at, last_question_at(30분 경계 판단)
- **chats** — id PK, thread_id FK, question, answer, created_at
- **feedbacks** — id PK, user_id FK, chat_id FK, unique(user_id, chat_id), is_positive, status, created_at
- **login_events** — id PK, user_id FK, created_at (활동 기록의 로그인 수 집계용)

관계: users 1:N threads 1:N chats, users·chats 1:N feedbacks. 스레드 삭제 시 chats·feedbacks ON DELETE CASCADE.

### 주요 가정 (요구사항이 정하지 않아 직접 결정한 것)

| # | 가정 | 결정 |
|---|---|---|
| 1 | 30분 경계 기준 | 스레드의 마지막 질문 시각(last_question_at)을 질문마다 갱신, 경과 시 새 스레드 |
| 2 | LLM에 보내는 이력 | 현재 스레드의 최근 10개 대화만 전송 (DB에는 전부 저장, 조회는 전체). `CHAT_HISTORY_SIZE`로 조정 |
| 3 | OpenAI 키 부재 시 | 대화 생성만 명시적 503. 테스트는 결정론적 fake로 키 없이 재현 |
| 4 | LLM 호출 실패 시 | chat 행을 남기지 않고 5xx 응답 (질문만 저장된 반쪽 데이터를 만들지 않음) |
| 5 | 스트리밍 | SSE(text/event-stream), 스트림 완료 후 DB 저장, 중간 실패 시 error 이벤트 |
| 6 | admin 생성 | 시드 마이그레이션(패스워드는 환경변수). 회원가입 API는 항상 member — role을 입력으로 받지 않음 |
| 7 | 대화 목록 페이지네이션 | 스레드 단위 페이징(0-base, 생성일시+id 정렬), 스레드 내부 대화는 오름차순 고정, size 상한 100 |
| 8 | "하루 동안" | 요청 시점부터 rolling 24시간(UTC). 로그인 수는 login_events 테이블로 집계 |
| 9 | 스레드 삭제 | 하위 chats·feedbacks까지 물리 삭제(CASCADE). soft delete는 요구에 없어 배제 |

## 구현 범위

요구사항의 필수 항목 12개(A1–R2)를 모두 구현했습니다. 위 매트릭스의 완료 판정은 전부 테스트로 덮여 있습니다.

**구현하지 않은 것**과 그 이유:

| 항목 | 이유 |
|---|---|
| Gradle 멀티모듈 분리 | 초기 단계에서 빌드 리스크 대비 이득이 낮다고 판단. 같은 의존 규칙을 패키지로 강제하고 승격 경로를 남겼다 |
| RAG(문서 적재·임베딩·검색) | 요구사항에 구현이 포함되지 않았다. 들어올 자리(`AiChatRequest.context`)만 비워뒀다 |
| 리프레시 토큰·로그아웃 | 요구는 "로그인 시 JWT 발급"까지다. 토큰 만료는 설정값으로 둔다 |
| 스트리밍 중단 시 부분 저장 | 실패 시 저장하지 않는 정책과 일관되게 두었다. 부분 답변을 남기려면 정책부터 정해야 한다 |
| Swagger/OpenAPI 문서 | 요구되지 않았고, API 계약은 이 문서의 표로 대신한다 |

## AI 활용 방식과 어려움

> 이 절은 이번 구현에서의 AI 활용 방식과 그때 겪은 문제를 정리한 것입니다.

**활용 방식은 세 갈래였습니다.**

첫째, **설계 단계의 독립 검증**. 구현을 시작하기 전에 요구사항 매트릭스·API 계약·데이터 모델·가정 목록을 먼저 문서로 고정하고, 그 문서를 별도의 AI 세션에 넘겨 "요구사항 대비 누락과 모순"만 지적하게 했습니다. 여기서 실제로 걸린 것이 **활동 기록의 로그인 수를 셀 근거 테이블이 없다**는 지적이었습니다. 스키마를 짜기 전에 발견해서 마이그레이션을 한 번만 썼습니다.

둘째, **도메인 단위 병렬 위임**. 피드백과 관리자 보고처럼 규칙이 명확한 CRUD는 도메인별로 작업을 나눠 병렬로 진행하고, 인증·대화처럼 동시성과 트랜잭션 경계가 얽힌 부분은 직접 작성했습니다. 나누는 기준은 "판단이 필요한가"였습니다.

셋째, **검증은 위임하지 않았습니다**. 테스트가 전부 통과해도 그것이 정상 동작의 증명이 아닌 경우를 아래 "가장 어려웠던 기능"에서 실제로 만났습니다.

**어려웠던 점.**

병렬로 나눠 작업하면 **파일 소유권을 미리 자르지 않는 한 서로의 코드를 덮어씁니다.** 그래서 각 작업 범위에 "생성 가능한 경로"와 "읽기만 할 경로"를 명시하고, 빌드는 한 곳에서만 돌리는 방식으로 통합했습니다.

또 하나는 **생성된 코드가 프로젝트 규칙과 충돌하는 비용**입니다. 예를 들어 Kotlin은 블록 주석이 중첩되기 때문에 주석 안에 경로 패턴(`admin/**`)을 쓰면 주석이 닫히지 않아 컴파일이 깨집니다. Java 감각으로는 걸리지 않는 함정이라, 통합 시점에 빌드를 돌려봐야만 드러났습니다.

## 가장 어려웠던 기능

**스트리밍(SSE) 응답 — 정확히는 스트리밍과 인증 필터의 상호작용이었습니다.**

`isStreaming=true`면 SSE로 토큰을 흘리는데, 구현 자체는 어렵지 않았습니다. 문제는 그 다음이었습니다. 통합 테스트를 붙이자 스트림은 정상적으로 나가는데 요청이 `ServletException: Unable to handle the Spring Security Exception because the response is already committed`로 끝났습니다.

원인은 **비동기 디스패치**였습니다. SSE는 서블릿 컨테이너에서 비동기로 처리되고, 스트림이 끝나면 요청이 필터 체인에 **한 번 더 들어옵니다.** 그런데 `OncePerRequestFilter`는 기본적으로 비동기 디스패치에서 실행되지 않습니다. 그래서 재진입 시점에는 JWT 필터가 돌지 않아 인증이 비어 있고, 인가 필터가 "인증 없음"으로 판단해 401을 쓰려 합니다. 하지만 응답은 이미 첫 토큰과 함께 커밋된 뒤라 상태코드를 바꿀 수 없어 예외로 터집니다.

해결은 JWT 필터가 비동기 디스패치에서도 동작하도록 여는 한 줄이었지만, **찾는 과정이 어려웠던 이유**는 증상이 원인과 멀었기 때문입니다. 스택트레이스는 Security를 가리키는데 실제 문제는 서블릿 비동기 처리 모델에 있었고, 비스트리밍 경로는 멀쩡했습니다.

여기서 얻은 것이 하나 더 있습니다. **이 버그는 "테스트를 짰기 때문에" 발견됐습니다.** 수동으로 curl을 한 번 던졌다면 토큰이 흘러나오는 것만 보고 정상이라고 판단했을 것입니다. 응답이 커밋된 뒤에는 오류를 HTTP로 알릴 방법이 없다는 제약도 이때 확인했고, 그래서 스트리밍 중 실패는 `error` 이벤트로 알리고 스트림을 닫는 방식으로 설계를 맞췄습니다.

**두 번째로 어려웠던 것은 스레드 경계의 동시성**이었습니다. "마지막 질문 후 30분"은 읽기와 쓰기 사이에 틈이 있는 규칙입니다. 같은 사용자가 질문 두 개를 동시에 보내면 둘 다 "최근 스레드 없음"으로 판정해 스레드가 두 개 생깁니다. 유저 단위 advisory lock으로 판정~저장 구간을 직렬화해 막았습니다. 유저 단위라 다른 사용자의 요청은 대기하지 않습니다.

## 설계 판단과 트레이드오프

- **AI 호출은 어떤 트랜잭션 안에도 두지 않았습니다.** 수십 초짜리 외부 호출이 DB 커넥션을 잡고 있으면 동시 요청 몇 개로 풀이 마릅니다. 그래서 `이력 조회 → (트랜잭션 밖) AI 호출 → 스레드 확정·저장`으로 쪼갰고, 자기 호출에는 프록시 AOP가 걸리지 않으므로 트랜잭션 경계를 별도 빈으로 분리했습니다.
- **스레드 생성을 AI 응답 이후로 미뤘습니다.** 먼저 만들면 호출이 실패했을 때 대화가 하나도 없는 빈 스레드가 목록에 남습니다. 첫 질문이면 이력도 비어 있으므로 미뤄도 잃는 것이 없습니다.
- **중복 방지는 유일 제약으로.** `exists`로 검사하고 넣으면 동시 요청 두 개가 검사를 통과해 둘 다 들어갑니다. DB 제약 위반을 409로 옮기는 쪽이 실제로 막힙니다.
- **이력은 최근 N개만 전송합니다.** 전체를 보내면 토큰과 지연이 대화 길이에 비례해 늘다가 컨텍스트 한도에서 실패합니다. 저장은 전부 하고 조회 API는 전체를 돌려주므로, 잘리는 것은 LLM에 보내는 분량뿐입니다. N은 설정값입니다.
- **목록은 스레드를 페이징하고 대화는 별도 조회로 채웁니다.** 컬렉션을 fetch join한 채 페이징하면 하이버네이트가 전체를 읽어 메모리에서 자릅니다.
- **정렬에는 항상 id를 덧붙였습니다.** 생성일시만으로 정렬하면 같은 시각의 행 순서가 보장되지 않아 페이지 경계에서 누락·중복이 납니다.
- **키 없이 돌아가는 가짜 응답을 기본 경로로 두지 않았습니다.** 시연 목표가 "API로 AI를 실제로 활용한다"이므로 실제 호출이 기본이고, 키가 없으면 조용히 흉내내는 대신 503으로 명시적으로 실패합니다. 다만 테스트는 결정론적 fake로 대체해 키 없이도 전부 통과합니다.

## 동시성에서 지키는 것과 지키지 않는 것

| 상황 | 처리 |
|---|---|
| 같은 사용자의 동시 질문 | 유저 단위 advisory lock으로 직렬화 — 스레드는 하나만 생긴다 |
| 같은 대화에 동시 피드백 | 유일 제약 위반 → 409 |
| 같은 이메일로 동시 가입 | 유일 제약 위반 → 409 |
| 외부 호출 중 커넥션 점유 | 트랜잭션 밖에서 호출하므로 점유하지 않는다 |
| 서로 다른 사용자의 동시 질문 | 서로 대기하지 않는다 (잠금 단위가 사용자다) |
